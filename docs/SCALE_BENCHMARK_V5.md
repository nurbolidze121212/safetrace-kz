# Фактический замер очереди и CPU-воркеров

Запуск [GitHub Actions 40206555664](https://github.com/nurbolidze121212/safetrace-kz/actions/runs/40206555664) на Linux x86-64, AMD EPYC 7763, 4 vCPU, 16 ГиБ RAM. В одном Compose работали API, Redis Streams, SQLite в общем томе и 1/2/4 отдельных процесса. Перед каждым замером выполнен прогрев настоящего OCR на каждом заявленном воркере. Все 96 коротких текстов и 24 PNG в каждом шаге дошли до финального состояния без ошибок. У изображений одинаковые авторские пиксели, но разные файлы и ключи: OCR-кэш не использовался.

| Воркеры | Текст, случаев/с | Текст p50 / p95 обработки | OCR, изображений/с | Изображение p50 / p95 обработки | p50 / p95 от постановки до результата, изображение |
|---:|---:|---:|---:|---:|---:|
| 1 | 22,94 | 34 / 44 мс | 0,434 | 2,26 / 2,48 с | 28,19 / 52,73 с |

Это скорость **осушения конечного пакета**, включая HTTP-постановку и опрос, а не гарантия стабильной ёмкости на бесконечном потоке. При 4 воркерах общий CPU почти не ускорил OCR после 2 воркеров; отдельное изображение стало обрабатываться дольше. У одного воркера очередь создала p95 ожидания изображения 50,60 с, у четырёх — 29,88 с. p50/p95 обработки и полный путь не следует смешивать. Прогрев, сырые записи по каждому случаю и характеристики раннера сохранены в [артефакте Actions](https://github.com/nurbolidze121212/safetrace-kz/actions/runs/40206555664) и [JSON](../reports/queue-ci/workers-1.json), [2](../reports/queue-ci/workers-2.json), [4](../reports/queue-ci/workers-4.json).

Путь: загрузка материала → SQLite + ограничение очереди Redis (128 активных) → воркер → дешёвая проверка кадра → OCR для непустых изображений → контекст и маршрут → досье и экран. Redis хранит задания с подтверждением, lease и повторным захватом; повторный запуск не должен смешивать анализы одного случая. Данные приложения остаются на машине с Docker.
