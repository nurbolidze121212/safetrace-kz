## Что входит в исходники

Код, lock-файлы, модели-манифесты без весов, авторские fixtures/наборы, тесты, технические отчёты, документация, лицензии сторонних компонентов. Для GitHub достаточно исходников: frontend строится при setup. Для отдельного передаваемого ZIP добавляется собранный frontend.

Не включать `.env`, API-ключи, `data/`, пользовательские оригиналы, резервные базы, `.venv`, `node_modules`, `models/`, логи, `tmp/`, токены и персональные входы. `.gitignore` уже исключает эти основные пути. Проверять также отслеживаемые файлы и историю: `.gitignore` не удаляет ранее закоммиченные секреты.

## Порядок публикации

1. Открыть текущую рабочую ветку и просмотреть `git status`, `git diff --check`, список публикуемых файлов. Сохранить локальные результаты проверки.
2. Создать пустой репозиторий в нужном аккаунте; без автоматически добавленных README/лицензии, чтобы не получить расходящуюся историю. Видимость выбрать осознанно; не назначать лицензию собственного кода без решения автора.
3. В корне проекта указать **реальный URL созданного репозитория**:

   ```powershell
   git remote add origin 'https://github.com/ACCOUNT/safetrace-kz.git'
   git push -u origin HEAD
   ```

   `ACCOUNT` — заполнитель, заменить своим аккаунтом. Если `origin` уже есть, сначала проверить его; не заменять чужой адрес автоматически. Аутентификация выполняется обычным GitHub/Git credential flow, ключи в команды/README не вставляются.

4. На GitHub открыть опубликованный README, изображения, документы и дерево файлов. Проверить, что ветка с текущими изменениями видна и выбрана корректно. Репозиторий исходников не является работающим публичным приложением.
5. Создать релиз для проверенного коммита и приложить исходный ZIP с manifest/SHA-256; данные пользователей не прикладывать. Состояние адаптеров и ограничения повторить в release notes.

Исходный комплект можно собрать и проверить штатным `scripts/package_source.py`; [точные команды и состав](INSTALL_AND_TRANSFER.md#создать-переносимый-исходный-комплект). Внешние `SHA256SUMS.txt` и `release.json` прикладываются рядом с ZIP. Они не должны ссылаться на несуществующий опубликованный релиз.

## Проверка перед защитой

Скачать опубликованную версию в новую папку, выполнить setup и preflight, затем пример с настоящим OCR, карту, контрпример и экспорт. Сравнить manifest, сохранить лог проверки и сведения о компьютере. Только после этого заявлять проверку скачанной публикации; другой каталог на прежнем ПК не называть независимой установкой на втором устройстве.

## Оформление без недостоверных обещаний

Не добавлять бейдж `100% accuracy`, зелёный CI без запуска CI, «real-time antivirus», «licensed casino verified» или «production ready», пока это не измерено. Не объявлять новый алгоритм, научную рецензию или внешнюю независимую оценку без основания. Можно показывать точные версии, воспроизводимые команды, результаты конкретного набора и открытый список ошибок.
